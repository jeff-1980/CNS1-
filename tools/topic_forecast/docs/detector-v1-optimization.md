# 探测器 v1：诊断、改造、自我迭代

## 0. 结论
1. **每日扫描目前没有用上预测模型。** 合并后的 `scan_daily/PROTOCOL.md` 的选题来源只有按轮次轮换的侧重点和各轮自己的文献检索；两者只共用杀死测试和失败台账的规则。唯一的联系是冰柜候选被手工录入。
2. 探测器目前是**三个互不相连的部件**（雷达、化验 v0、数据地图），没有闭环：雷达的输出没人消费，扫描和杀死测试的结果没回到探测器。
3. **可以自我迭代，但只迭代有足够反馈的部分**：雷达（有真实标签，每年自动刷新和滚动回测）、种子来源的命中率（Beta 二项后验）、规则提议（Sonnet 子代理提议，jeff 批准）。**不能自动迭代的**：化验权重（3 个存活 vs 35 个死亡，且字段是事后填的）、闸门放松、LLM 打分。

## 1. 诊断（依据：本项目已有数据）
| 现象 | 数据 | 含义 |
|---|---|---|
| 雷达测的是注意力，不是金子 | 最重要特征是已有共现数；前 20 名多是"工程对象 × 通用 AI 方法"；泛 AI 搭档主题（对抗鲁棒性、可解释 AI）占比高 | 标签（共现涌现 ≥10）奖励热门 |
| 存活方向不在热区 | 与存活方向对应的 OpenAlex 主题：风能研发 规模第 68 百分位、3 年增速第 45 百分位；电力系统可靠性与维护 49 / 46；热门的"机器故障诊断"和"可靠性与维护优化"是第 94 / 92、90 / 74 | 存活来自"数据先行"，不是"热度跟随" |
| 失败多死在便宜的闸门，但进入测试后死在基线 | 322 条失败记录首要原因：H1 82、H4 82、数据 56、拥挤 47、H3 28、H2 15、基线 7、K-sim 2；到了杀死测试阶段，D1–D6、焊接、冰柜等多死于基线/安慰剂/真值模拟 | 前端闸门由文字判断，后端闸门（基线）才是真正的筛子，但它最贵 |
| 化验 v0 回放 AUC 0.986 | 台账字段和权重出自同一批教训 | 只能说明规则不自相矛盾；评估类型 = relative_only |
| 回路是开的 | 扫描不读雷达；雷达不读失败台账；冰柜是手工入池 | 无法测量"雷达种子是否比自由检索命中率更高" |

## 2. 改造（按收益排序）
**A. 先把 H2 前置并工具化（最大收益）。** 把冰柜脚本抽成通用工具：输入"设备/个体 × 时间序列 × 事件表"，做"事件前 vs 同个体对照日 + 同个体日期随机移位安慰剂"检验，不训练模型，几分钟出结果。候选一进池就先跑小样本，再决定要不要下全量数据。前兆类想法默认高风险（已写入扫描规则 H2 补充 3）。

**B. 加数据侧种子，和主题侧种子并行。** 存活方向全是数据先行。做法：数据地图每一行 × 问题模板（暴露-响应、自然实验/干预前后、政策冲击、元研究/复现）→ 用 OpenAlex 检索该数据集名字的论文数作为拥挤度 → 输出"数据 × 模板"排序。主题侧种子是雷达化验后的主题对（已生成 `seeds/seeds_2026-11-04.csv`）。

**C. 重定雷达目标，使之更接近我们要的东西。**
- 标签从"共现涌现"增加一个版本："涌现且伙伴主题不拥挤"，并给泛 AI 方法类搭档单独分组；
- 增加 NC/SA 版标签（需要对象对层面的 NC/SA 共现，约 2 美元预付额度）；
- 领先指标：Scientific Data / Zenodo 新发布的运行数据集（数据先于论文出现）。

**D. 前端闸门自动化。** 78% 的失败死在文字级闸门（H1/H4/数据/拥挤），这些可由卡片字段 + 化验打分在不花子代理 token 的情况下先拒掉；后端闸门（基线）留给真实数据。

**E. 把回路接上。** 每个种子带编号 → 候选 → 结局（存活/死因码）；按种子来源（雷达主题对、数据侧、自由检索）统计命中率。

## 3. 自我迭代：能做什么，不能做什么
| 部件 | 能否自动迭代 | 方式 | 护栏 |
|---|---|---|---|
| 雷达模型 | 能 | 每月只抓最近一年（约 0.3–0.5 美元），滚动起点回测，输出 K1/K3 趋势 | 判据冻结；新模型须在"更晚的起点"上不输旧模型才替换 |
| 前瞻检验 | 能（慢） | 冻结 T=2025 预测并写成预注册，2028 年用 OpenAlex 核对 | 哈希 + 提交时间戳；见 `PREREG_FORECAST_T2025_FROZEN.md` |
| 种子来源分配 | 能（小样本） | 每个来源一个 Beta(1,1) 后验，记录"种子→入池→通过杀死测试"的转化；扫描轮次按后验分配 | 保底：每个来源至少占 1/4 的轮次，避免过早收敛 |
| 规则提议 | 半自动 | 同一模式 ≥3 个独立失败 → Sonnet 子代理起草规则补充 → 回放：3 个存活方向不得被新规则拒掉 → jeff 批准才生效（H2 补充 1–3 就是这样手工产生的） | 只能收紧或加新闸门，不得自动放松；规则带版本和日期 |
| 化验权重 | **不能** | 3 个正样本无法拟合；字段是事后填的 | 保持手工权重 + 人工修订；等 ≥10 个存活后再按时间顺序拟合 |
| LLM 新颖性打分 | **不能** | 与人评相关仅约 0.5 | 不用于排序 |
| 自动改 PROTOCOL | **不能** | — | 避免对少数案例过拟合 |

## 4. 落地顺序
1. 今天：冻结 T=2025 预测（预注册）；生成种子文件；交给扫描线程由 jeff 决定是否接入（建议先做 A/B 对照：一半轮次用雷达种子，一半沿用原流程）。
2. 本周：通用 H2 工具包（冰柜改造）；数据侧种子原型；增量刷新脚本（先写后跑）。
3. 两周内：种子来源命中率看板；规则提议流程试跑一次（用已有的 3 次手工规则补充回放验证）。
4. 每月：增量刷新 + 滚动回测。
